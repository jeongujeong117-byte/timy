제품 원페이저

서비스명 미정. 편의상 약속앱으로 표기.

한 줄 정의

대학생이 카톡방에서 단발성 약속을 잡을 때, 로그인과 뎁스를 없애서 링크 하나로 끝내는 일정 조율 도구.

이 앱의 본질

시간 계산 도구가 아니다. 단톡방의 눈치 게임을 구조로 대체하는 도구다.

"다들 언제 돼요?" → 각자 답장 → 정리 → 재확인 → 확정으로 이어지는 왕복을, 링크 한 번으로 압축하는 것이 목적이다.

페르소나
대학생
단발성(정기 모임 아님), 즉각적(2~5일 내 약속)
카카오톡 단톡방이 주 채널
시간표는 에브리타임, 약속은 카톡에 있음. 구글 캘린더 사용률은 미확인
참여자 3~8명 규모
문제 (AS-IS)
"다들 언제 시간 되세요?"
  → "저는 O요일 됩니다" (각자 답장, 순차적)
  → 누군가 정리
  → "그럼 이 날 괜찮으신가요?"
  → 예 / 아니오
  → (아니오면 처음으로)
  → 확정되면 각자 캘린더에 따로 기록

기존 조율 툴을 쓰더라도:

링크 받음 → 로그인 → 시간 설정 → 결과 확인
  → 여전히 카톡으로 돌아가서 "이 날 괜찮나요?" 재확인

핵심 병목

왕복 횟수가 인원수에 비례해 늘어남
로그인이 참여 문턱
시간 입력 뎁스가 깊음
결과를 봐도 확정이 안 됨 — 결국 카톡으로 회귀
TO-BE
카톡방 → 링크 탭 → (로그인 없음) → 안 되는 시간만 빼기 → 제출
  → 실시간 히트맵 + TOP 3 추천
  → 주최자가 확정 버튼 1번
  → 카톡 공유 카드 자동 생성 + 각자 캘린더로 내보내기
MVP 성공 기준 (숫자로)
개설: 3탭 이내
참여: 로그인 0회, 스크롤 최소, 5탭 이내
카톡 왕복: 링크 공유 1번 + 확정 통보 1번 = 총 2회

이 숫자를 넘기는 기능은 MVP에 넣지 않는다.

차별점 (우선순위 순)
순위	내용	MVP 포함
1	극한으로 짧은 플로우	O
2	한눈에 들어오는 가시성	O
3	확정까지 앱 안에서 끝내기	O (단, 가치 검증 필요)
4	캘린더/시간표 가져오기	X — 2차

4번은 MVP에서 제외. 연동 = OAuth = 로그인이라 1번과 충돌한다. 연동은 "안 해도 되는데 버튼 누르면 편해지는" 선택 기능으로만 존재한다.

기본값(옵트아웃)은 양쪽 통일. 한쪽만 다르면 같은 방 안에서 응답 성격이 갈려 데이터가 오염된다.

데이터 모델은 입력 방식과 무관하게 (방, 날짜, 시간, 사람, 가능여부)만 저장.

옵트아웃 기본값의 근거와 리스크

근거

탭 횟수 감소 (안 되는 시간은 보통 1~2칸)
기본값 효과 — 수집되는 가용 시간 총량 증가

리스크와 대응

아무것도 안 빼고 제출 → "한 칸도 안 뺐는데 정말 다 가능한가요?" 확인 1회
"이미 누가 골라놨나?" 오해 → "안 되는 시간을 눌러 빼주세요" 명시 + 첫 진입 시 한 칸 빠지는 짧은 안내
연동 로드맵 (MVP 이후)
직접 입력 + 로컬 저장 — 연동 0개. 두 번째 사용부터 시간표 자동 불러오기
구글 캘린더 가져오기 — 정식 API. OAuth 연습
시간표 이미지 인식 — 에타 시간표 캡처 업로드 → AI가 읽기

가져온 일정은 배경에 표시하되 자동 반영 후 수정 가능하게. 캘린더에 일정이 있다고 반드시 불가능한 건 아니다 (옮길 수 있는 약속 vs 시험). 최종 결정권은 사용자에게 남긴다.

확정된 약속은 캘린더로 내보내기. 가져오기/내보내기가 같은 연동 하나로 닫힌다.

파트 1 요약
병목은 "시간 계산"이 아니라 "왕복"이다. 참가자 수가 늘수록 반복 횟수와 시간이 함께 증가.
응답 순서가 결과를 바꾼다. 초기 응답자가 후기 응답자보다 결과에 더 큰 영향.
남의 응답이 보이는 폴이 성사율이 더 높다. 정확성 ↔ 성사율은 맞바꿈 관계.
사람들은 정직하게 답하지 않는다. 열린 폴에서 전략적·협조적 응답이 관찰됨.
집단주의 문화권에서 이 경향이 더 강하다. 한국 시장에 직접 영향.
실증 자료
Doodle 실험 — 왕복이 병목 [중]

96명에게 4~6인 저녁식사, 6~8인 비즈니스 미팅, 10~15인 저녁식사를 잡게 함.

왕복 커뮤니케이션이 가장 큰 시간 소모 요인
반복 횟수와 소요 시간이 참가자 수에 비례해 증가
성별·연령·학력은 소요 시간에 영향 없음

의미: 병목의 원인이 개인 특성이 아니라 **구조(인원수 × 왕복)**에 있다. 사용자 교육이나 "총무가 잘하면" 되는 문제가 아니다.

주의: Doodle이 자사 제품 효과를 보이려 수행한 실험. 방향성은 신뢰하되 구체적 절감 수치는 인용하지 말 것.

정보 캐스케이드 [강]

Romero, Reinecke, Robert (CSCW). Doodle 폴 130만 건 이상 분석.

일정 조율 과정에서 캐스케이드 효과 발생
초기 응답자가 후기 응답자보다 결과에 더 큰 영향

의미: "먼저 답한 소수가 사실상 결정권을 갖는다." 늦게 답하는 사람은 굳어진 흐름을 따라갈 뿐.

공개 폴이 성사율이 높다 [강]

같은 연구가 인용한 선행 결과.

다른 사람 응답을 볼 수 있는 폴이 숨기는 폴보다 성공 확률이 높음

의미 — 딜레마

숨김 → 솔직한 응답, 그러나 약속이 안 잡힘
공개 → 눈치 봄, 그러나 약속이 잡힘

이 앱의 목적이 "정확한 데이터 수집"이 아니라 "약속 성사"라면 기본은 공개가 맞다. 숨김은 실험 대상으로만.

전략적 응답 [강]

Zou, Meir, Parkes (CSCW). Doodle 폴 약 34.5만 건 분석.

열린 폴 참가자는 더 "협조적"으로 행동
매우 인기 있거나 매우 인기 없는 시간대에 추가로 동의하는 경향
닫힌 폴 참가자와 다른 행동 패턴

원논문의 문제 제기:

참가자가 그 시간에 임시로 묶이는 걸 피하려고 가능한데도 표시하지 않는다면? 합의를 방해하고 싶지 않아서 덜 편한 시간에도 가능하다고 표시한다면?

의미: 히트맵의 색은 "가용성"이 아니라 "가용성 + 사회적 압력 + 전략"의 합이다. 순수한 데이터로 취급하면 안 된다.

문화 차이 [중]

Reinecke 외 (CSCW 2013). 211개국 Doodle 폴 150만 건 이상.

집단주의 문화권 참가자는 더 일찍 응답
더 적은 선택지에 동의
그러나 더 많은 합의에 도달
열린 폴에서 서로 더 많이 조율

한국 적용 시 예상 행동

가능 시간을 좁게 답함
서로 맞춰주려는 조정이 강함

→ 좁게 답하는 게 기본값이라면, 가용 시간을 넓히는 장치가 서구보다 더 필요. 옵트아웃 기본값 채택의 근거 중 하나.

주의: 2013년 데이터. 국가 단위 문화 지표를 개인 행동에 적용하는 방식은 생태학적 오류 비판이 있음. 방향성 참고로만.

경매 방식 제안 — 총량 제한과 정직성 [약, 아이디어 참고용]

Xu (Harvard 학사논문, 2010). Doodle 대안으로 경매 메커니즘 제안.

근거: 참가자가 각 시간대에 가치를 매길 수 있음 + Doodle에서 거짓·불완전 정보 제공 경향

핵심은 "강도 표현"이 아니라 "총량 제한"이다.

총량 제한이 없으면 → "다 좋아요"가 최선 전략 → 정보가 무의미해짐
총량이 정해지면 → 흩뿌리면 정말 원하는 곳에 힘을 못 실음 → 진짜 선호대로 배분하는 게 이득

= 정직하라고 요구하는 게 아니라, 정직한 게 이득이 되게 규칙을 짜는 것 (메커니즘 디자인)

우리 앱 적용안 (경매 자체는 플로우와 충돌하므로 원리만)

가능 / 선호 2단계
"선호"에만 개수 제한 (예: 최대 3칸) → 미니 예산 역할
집계 시 선호 2점, 가능 1점 가중치
이미 칠한 칸을 한 번 더 탭하면 선호로 전환 → 뎁스 증가 없음

검증 안 됨. 3칸 제한이 정직한 응답을 유도하는지, 아니면 귀찮아서 아무 데나 찍게 만드는지는 직접 확인 필요.

결정 피로 / 자아 고갈 — 대규모 다기관 재현 실패

기획 근거로는 기본값 효과 / 계획 오류 / 절차적 공정성에 무게를 둘 것.

절차적 공정성 — 이 앱의 존재 이유

핵심 발견: 사람들은 결과가 불리해도 과정이 공정했다고 느끼면 수용한다. 특히 발언권 효과 — 내 의견이 반영될 기회가 있었다는 사실만으로 만족도가 올라감.

단톡방에서 총무가 일방 통보하는 것과, 모두가 응답하고 자동 집계된 결과를 보는 것은 같은 시간이 나와도 수용도가 다르다.

→ 이것이 원페이저의 "눈치 게임을 구조로 대체" 문장의 이론적 근거. → 동시에 앱이 자동 확정하면 안 되는 이유. 앱은 TOP 3을 계산해 보여주고, 주최자가 누른다. 자동 확정은 발언권 효과를 깨뜨린다.

아직 근거가 없는 것 (직접 검증 필요)
가설	상태
왕복이 병목이다	실증 있음
응답 순서가 결과를 좌우한다	대규모 실증 있음
응답 공개가 성사율을 높인다	실증 있음
확정 단계에서 병목이 생긴다	직접 자료 못 찾음
대학생 단발성 약속의 조율 비용	자료 못 찾음 (기업 데이터만 존재)
로그인이 참여율을 떨어뜨린다	일반 전환율 통념은 있으나 이 맥락 실증 못 찾음
선호 개수 제한이 정직도를 높인다	미검증

아래 세 개가 이 기획의 핵심 전제인데 근거가 비어 있다.

직접 검증 방법 (권장)

주변 대학생 10~15명에게 묻는다.

"가장 최근에 잡은 약속, 처음 말 꺼낸 시점부터 확정까지 며칠 걸렸고 메시지가 몇 번 오갔나요?"

표본이 작아도 기업 통계를 억지로 끌어오는 것보다 훨씬 설득력 있다.

주의 — 기업 회의 통계를 그대로 쓰지 말 것

널리 인용되는 "비생산적 회의로 연 3,990억 달러 손실" 같은 수치는 스케줄링 업체 추정치가 재인용으로 굳어진 것. 원출처 확인 없이 쓰지 말 것.

또한 직장인은 조율 실패 비용이 크지만 대학생은 안 만나면 그만이다. 비용 구조가 달라 논리에 구멍이 생긴다.

단 하나 유용한 참고: 회의의 35%가 시작 24시간 이내에 생성되고, 일주일 이상 앞서 잡히는 건 8%뿐. → "즉각적·단발성" 페르소나 설정과 방향 일치.

미진행 — 파트 2·3
파트 2: 미시(약속 시 사람들 사이 작동하는 이론) / 거시(의사결정 이론) 상세 조사
파트 3: 이를 대처·변경하는 방법론 (넛지, 메커니즘 디자인, 그룹 의사결정 퍼실리테이션 등)

필요할 때 이어서 진행할 것.레퍼런스 분석
조율 서비스는 세 종류다 (헷갈리지 말 것)
유형	구조	예시
A. 그룹 조율 (N:N)	모두가 가능 시간을 내고 교집합을 찾음. 참가자 대등. 로그인 불필요	When2meet, Doodle, 날잡아
B. 예약형 (1:N)	한 사람의 가능 시간이 정해져 있고 나머지가 예약. 주최자 계정·캘린더 연동 필수	Calendly, Cal.com, SavvyCal
C. 사내 자동화	전사 캘린더가 서버에 있으니 빈 시간을 그냥 계산	Outlook 일정 도우미, 구글 캘린더 회의 시간 찾기

우리는 A다. B는 성격이 다른 앱이고, C는 개인 프로젝트로 불가능하다.

직접 뜯어본 레퍼런스 4개
1. 날잡아 (국내)

플로우

정보 온보딩(로그인 X) → 참여 상태·겹치는 시간 목록 → 시간표에서 날짜·시간(1시간 단위) 클릭 → 링크 복사(우측 버튼)

문제점

초반 정보 온보딩이 귀찮음
시간대를 전부 개별 클릭해야 함 (드래그 없음)
2. 모여봐요 (국내)

플로우

약속 만들기 → 이름 → 날짜 선택(주말/주중 카테고리 클릭) → 시간 설정(시간대 별도 클릭, 시간대별 설정) → 약속 만들기 → 투표 페이지 이동 → 선호·비선호 클릭 → 결과 보기 → 종합 페이지

문제점

시간대 하나 입력하는 데 뎁스와 과정이 너무 많음
투표 → 결과 보기 → 종합이 3단계로 쪼개져 있음

배울 점: 선호/가능/불가능 3단계 구분은 참고할 만함

3. WhenSee (국내)

플로우

새 일정 만들기 → 로그인 → 날짜 범위/개별 날짜 선택 → 캘린더 칩 클릭 → 다음 →
시간대 설정 팝업 → 시간 항목 분류 → 시작·종료 시간 → 모임 정보 온보딩(이름/주최자) →
로딩 화면 → 결과(일정 정보 + 초대 + 가능 시간대 + 겹치는 시간대)

문제점

세로 스크롤이 너무 김. 한 번에 정보가 눈에 안 들어옴
로그인이 초반에 있음
4. Calendly (해외, 유형 B)

플로우

정보 온보딩: 이름 → 목적 → 인원 → 타 앱 연결 → 만나는 주기 → 회의 도구 연동

문제점

온보딩이 길고, 우리 페르소나와 목적이 다름
참고만 하고 베끼지 않을 것
When2meet — 이 장르의 원형. 최소 기능이 뭔지 배우기엔 최고. 로그인 없음 + 격자 드래그 + 히트맵, 이 셋이 전부. 단 모바일에서 칸이 손가락보다 작아 사실상 실패한 UI.
Rallly — 오픈소스. 코드 구조 참고 가능
Lettucemeet — When2meet을 요즘 UI로
Whennot2meet — "안 되는 시간"을 수합하는 역발상. 우리 옵트아웃 기본값의 선례
SavvyCal — 링크 받은 사람이 자기 캘린더를 겹쳐 볼 수 있음. 연동 아이디어는 여기서 가져온다
모바일 시간 선택 — 세 가지 레이아웃 패턴
A. 전체 그리드 (When2meet 방식)
조망은 최고 / 칸이 너무 작아 모바일에서 실패
B. 날짜 칩 + 시간 리스트 (예약 앱 표준)
날짜를 위에서 고르고 그날 시간만 아래에 크게
캐치테이블, 똑딱, 네이버 예약, Calendly 모바일이 전부 이 구조
터치 쉬움 / 전체 조망 불가 — 조율 앱엔 이게 치명적
C. 하루씩 순차 (토스 방식) ← 우리가 채택
"한 화면에 질문 하나". 심리적 부담 적고 완주율 높음
뎁스가 날짜 수만큼 늘어남 → 후보 날짜 3~5일 제한으로 해결
하루 8칸이면 드래그 불필요. 탭이 더 편함
최종 결정

입력은 C, 결과 조망은 A. 입력 화면과 결과 화면은 요구가 정반대다. 하나로 통일하려니 답이 안 나왔던 것.

모바일 UI 참고처
참고처	무엇을 볼 것
토스 송금·인증 플로우	한 화면 한 질문. "화면이 여러 개인데 왜 안 답답한지"
캐치테이블 / 똑딱	날짜 칩 가로 스크롤, 시간 슬롯 크기
인터파크·멜론티켓 좌석 선택	극단적 밀도를 핀치줌 + 미니맵으로 푸는 방식 (결과 화면 아이디어)
에브리타임 시간표	대학생이 이미 익숙한 그리드. 결과 화면에 쓰면 학습 비용 0
시장 현황 메모

국내에 이미 여럿 있다 — 날잡아, WhenSee, 모여봐요, 이때 등. 공통적으로 카카오톡 공유 + 로그인 없는 참여를 내세운다. = 국내에서 이 둘은 기능이 아니라 생존 조건.

연습 프로젝트이므로 경쟁 자체는 문제가 아니지만, "나는 뭘 다르게 하는가"를 명확히 해두는 것이 기획의 축이 된다. → 우리 답: 플로우 길이와 확정까지 책임지기.
